\begin{abstract}
Typed decisions cut an agent memory system's decision cost and latency and help retrieval under a small budget; they do not change answers after facts change, and a small zero-shot model cannot make them. Memory systems make an LLM call for every write decision, which makes revisiting the store unaffordable, yet most of that work is choice among fixed options. In engram, an LLM extracts facts and every decision is a typed question answered by a hosted decision model (Jev). With extraction held identical to mem0 2.1.0's, typed decisions cut decision-layer cost by 70.0$\times$\src{bench/results/e2\_llm\_\_dev.json ÷ bench/results/e2\_jev\_\_dev.json} and median decision latency by 27.6$\times$\src{bench/results/e2\_llm\_\_dev.json ÷ bench/results/e2\_jev\_\_dev.json}, with equal dev accuracy (31/35\src{bench/results/e2\_jev\_\_dev.json} against 31/35\src{bench/results/e2\_llm\_\_dev.json}). On 610\src{bench/results/heldout\_report.json} held-out LoCoMo questions under a three-memory retrieval budget, engram answers +8.7\src{bench/results/mem0\_token\_matched\_\_heldout\_pooled\_\_k6.json} points more than mem0 at matched context tokens (95\% CI +5.2\src{bench/results/mem0\_token\_matched\_\_heldout\_pooled\_\_k6.json} to +12.1\src{bench/results/mem0\_token\_matched\_\_heldout\_pooled\_\_k6.json}); at k=20 the systems tie (+0.8\src{bench/results/heldout\_report.json}, CI -2.3\src{bench/results/heldout\_report.json} to +3.9\src{bench/results/heldout\_report.json}). A belief-state store policy over-closed no labeled keep item. Two results are negative: closing stale facts does not change answers on current benchmarks, and the 421M\src{convai2026laya (model card)} base checkpoint of the open-weights decision model Laya, used zero-shot as its documentation advises against, does not make the relational decisions. Code, prompts and per-question results are released.

\end{abstract}
\section{Introduction}
\textbf{The cost problem.} A memory system for an LLM agent turns conversation into facts it can retrieve later. Each write has two parts:

\begin{itemize}
\item Extraction: what facts does this message state?
\item Decisions: is each fact new, a duplicate, a refinement, or a change to something already stored? Is it worth keeping? Is it sensitive?
\end{itemize}
\textbf{Concurrent work.} The architectural idea of routing memory decisions to a typed decision model was reached independently by Jev-Mem \citep{jiang2026jevmem}, which uses Jev for typing, relation construction, query routing, budget allocation, traversal, candidate scoring and stopping. It reports a LoCoMo judge score of 0.777\src{jiang2026jevmem (reported LoCoMo judge score)} with a 158\src{jiang2026jevmem (reported build time, s)} s build and 0.93\src{jiang2026jevmem (reported query time, s)} s query against A-MEM \citep{xu2025amem}, Nemori, MemoryOS and MAGMA \citep{jiang2026magma}. It does not isolate the decision layer, evaluate updates or closes, measure calibration, or use a held-out split or confidence intervals. Separately, a community article reranked AtMem's top-10 with Jev on 1,986\src{taghia2026atmem (LoCoMo questions)} LoCoMo questions and measured the effect at the ranking level: MRR@5 rose from 0.4259\src{taghia2026atmem (MRR@5, AtMem)} to 0.5868\src{taghia2026atmem (MRR@5, AtMem + Jev)} and Recall@1 from 0.3399\src{taghia2026atmem (Recall@1, AtMem)} to 0.5423\src{taghia2026atmem (Recall@1, AtMem + Jev)} \citep{taghia2026atmem}. This paper's contribution is the controlled measurement: an identical-extraction ablation of the decision layer, its calibration, the safety of the store it drives, the rerank effect on answers with a matched-context control, and the negatives.

In current open-source systems both parts are LLM calls. mem0 2.1.0's default \texttt{add()} makes a single LLM call per message with its additive extraction prompt, and has no separate update or delete step (\texttt{mem0/memory/main.py}, \texttt{Memory.\_\allowbreak{}add\_\allowbreak{}to\_\allowbreak{}vector\_\allowbreak{}store}; prompts reproduced in Appendix B). An LLM call per decision is expensive enough that nothing re-examines the store afterwards. Facts that stopped being true stay in it.

\textbf{The observation.} The decisions are choices among options fixed in advance. That is the setting typed decision models are built for. They return a calibrated probability over a fixed option set in one short request, and they cost far less than generating text.

\textbf{Contributions.}

\begin{enumerate}
\item With extraction held identical, typed decisions replace an LLM decision layer at 70.0$\times$\src{bench/results/e2\_llm\_\_dev.json ÷ bench/results/e2\_jev\_\_dev.json} lower cost and 27.6$\times$\src{bench/results/e2\_llm\_\_dev.json ÷ bench/results/e2\_jev\_\_dev.json} lower median latency with no measured accuracy loss (\S{}5.1).
\item A belief-state store policy with reversible, gated closes over-closes no labeled keep item, and its v3 rule removes a weak-evidence failure that closes true facts (\S{}3.4, \S{}5.3).
\item Under a three-memory budget a listwise Jev rerank puts engram +8.7\src{bench/results/mem0\_token\_matched\_\_heldout\_pooled\_\_k6.json} points ahead of mem0 at matched context on 610\src{bench/results/heldout\_report.json} held-out questions, and the systems tie at k=20 (\S{}5.2).
\item Closing stale facts does not change answers on current benchmarks, and a zero-shot base checkpoint of an open-weights decision model does not make the relational decisions (\S{}5.5, \S{}5.6).
\end{enumerate}
\textbf{Scope.} We compare against one baseline (mem0 OSS 2.1.0) on one benchmark (LoCoMo: one development conversation and four held-out conversations). We use update sets written by the system's author, and one hosted decision model (Jev, \texttt{jev-1.13.0}).

We did not test:

\begin{itemize}
\item Zep/Graphiti or Letta
\item LongMemEval
\item other extraction, answer or judge models
\item multi-user stores
\item non-English text
\end{itemize}
\section{Background}
\subsection{How memory systems make write decisions}
\begin{itemize}
\item \textbf{mem0} \citep{chhikara2025mem0} (2.1.0) extracts facts with one LLM call per message. The prompt receives the new message, the last 10\src{src/engram/flags.py (extract\_last\_k, as mem0 2.1.0)} messages and the 10\src{src/engram/config.py} most similar existing memories, and emits only additions. Its older update step, which asked an LLM to label each new fact as ADD, UPDATE, DELETE or NONE against existing memories, is still shipped as \texttt{DEFAULT\_\allowbreak{}UPDATE\_\allowbreak{}MEMORY\_\allowbreak{}PROMPT}. We use it as the LLM decision layer in \S{}5.1.
\item \textbf{Zep's Graphiti} resolves entities and invalidates edges with LLM calls \citep{rasmussen2025zep}.
\item \textbf{ByteRover} curates a hierarchical context with an LLM; its retrieval is a five-tier progressive strategy that answers most queries in under 100\src{nguyen2026byterover (sub-100 ms tier resolution)} ms without LLM calls and escalates to agentic reasoning only for novel questions \citep{nguyen2026byterover}.
\end{itemize}
\subsection{Typed decision models}
A typed decision model takes a shared \emph{state} (JSON) and a set of questions. Each question is one of:

\begin{itemize}
\item a choice among named options, each with a rubric
\item a yes/no (``noul'') question
\item a score
\end{itemize}
It returns a probability distribution per question.

\textbf{Jev.} We use Jev through TypeSafe's API: model \texttt{jev-1.13.0}, priced at 0.042\src{src/engram/config.py (USD per million input tokens)} USD per million input tokens (\texttt{src/engram/config.py}). Its documentation gives a limit of 255\src{typesafe2026jev (max options per Choice)} options per choice question \citep{typesafe2026jev}. Measured latency is flat in request size (\S{}5.7).

\textbf{Laya.} Laya is an open-weights model with the same request format. We ran checkpoint convaiinnovations/laya\src{bench/results/e4\_belief\_v2\_laya\_\_dev\_updates\_\_k3.json} locally through the laya-mlx port on an Apple M2 Pro\src{bench/results/e4\_belief\_v2\_laya\_\_dev\_updates\_\_k3.json} with 32\src{bench/results/e4\_belief\_v2\_laya\_\_dev\_updates\_\_k3.json} GB. It reads at most 512\src{bench/results/e4\_belief\_v2\_laya\_\_dev\_updates\_\_k3.json} tokens per question, of which at most 192\src{bench/results/e4\_belief\_v2\_laya\_\_dev\_updates\_\_k3.json} go to the instructions and options. This is the 421M\src{convai2026laya (model card)} base checkpoint. Its model card reports zero-shot typed-decision accuracy of 0.362\src{convai2026laya (base checkpoint, typed-decisions, zero-shot)} against a 0.318\src{convai2026laya (random baseline)} random baseline, calls it ``a fast base to specialise, not a zero-shot decision engine,'' and offers a separate checkpoint fine-tuned for typed decisions \citep{convai2026laya}. We used the base checkpoint zero-shot.

\subsection{LoCoMo and its limits}
LoCoMo \citep{maharana2024locomo} contains long multi-session conversations with questions in four scored categories.

\textbf{It barely tests updates.} In the first 215\src{bench/results/e2\_jev\_\_stress.json} messages of conv-26, an LLM labeler (claude-sonnet-4-6, prompt in \texttt{bench/stale.py}) found 2\src{bench/results/e0\_baseline\_\_stress.json} claims that a later message makes no longer true (\texttt{bench/slices/conv26\_\allowbreak{}superseded.json}).

\textbf{Public scores are not comparable.} Published LoCoMo scores for the same systems differ between the systems' own reports and third-party reports \citep{mem0blog2026benchmarks,byteroverblog2026benchmark}. We do not quote those numbers. All comparisons here run both systems under one protocol.

\textbf{Write path.}

\begin{enumerate}
\item An LLM extracts facts from a message. In the experiments this uses mem0's prompt and inputs; \S{}4.2.
\item Each fact goes to Jev as a single request. The request carries the fact questions and one \texttt{relation\_\allowbreak{}to\_\allowbreak{}candidate} question for each of up to 10\src{src/engram/config.py} candidate facts.
\item A policy layer (\S{}3.3) and a belief state (\S{}3.4) turn the answers into store operations.
\item The store is SQLite plus NetworkX. Facts are edges with validity windows, and every decision is logged with its probabilities.
\end{enumerate}
\textbf{Read path.}

\begin{enumerate}
\item Embed the question and take the cosine top-k.
\item Jev reranks the candidates with one yes/no relevance question per candidate, plus a \texttt{query\_\allowbreak{}relation} question that can pull in facts by relation type.
\item Add history: the facts each retrieved fact superseded.
\item Render compact lines for the answer model: the date the fact was said, the fact, and the verbatim source quote.
\end{enumerate}

\subsection{Policy layer}
Decisions act only through explicit rules (\texttt{src/engram/pipeline/write.py}):

\begin{itemize}
\item \textbf{Thresholds.} A decision acts at $p \ge$ 0.85\src{src/engram/config.py}. A superseding relation (update, contradiction, negates) below 0.60\src{src/engram/config.py} is escalated to an LLM, using mem0's update prompt. Anything in between is stored as tentative.
\item \textbf{Temporal gate.} An old edge can close only if the new fact is current or past: $P(\text{current}) + P(\text{past}) \ge$ 0.85\src{src/engram/config.py}. Planned and hypothetical statements never close anything.
\item \textbf{Cardinality.} Each relation type is single- or multi-valued. \texttt{contradiction} closes only a sibling (same subject and relation) on a single-valued relation. \texttt{update} may also close a multi-valued sibling. \texttt{negates} (the new fact says the old one stopped) may close any edge.
\item \textbf{Two-phrasing agreement.} The first piece of evidence against an edge must be confirmed by a second phrasing of the relation question (\texttt{relation\_\allowbreak{}to\_\allowbreak{}candidate\_\allowbreak{}recheck}). Otherwise it does not count.
\item \textbf{Plans.} A dedicated yes/no question, \texttt{plan\_\allowbreak{}fulfilled}, asks whether a new fact reports that a stored plan has happened. At $p \ge$ 0.85\src{src/engram/config.py} the plan closes with reason \emph{fulfilled}.
\item \textbf{Merges are links.} A duplicate becomes a \texttt{same\_\allowbreak{}as} link, collapsed at retrieval and removable. Text is never merged.
\item \textbf{Overrides.} An explicit request to remember overrides \texttt{worth\_\allowbreak{}remembering}. A credential is redacted before storage, whatever the other answers say.
\end{itemize}
\subsection{Belief state}
Each edge $i$ carries a belief $b_i \in [$ 0.02\src{src/engram/pipeline/belief.py}, 0.98\src{src/engram/pipeline/belief.py} $]$ that it is currently true. A typed answer $z$ about the edge, with probability $q$ for its chosen label, updates it in log-odds:

\[\operatorname{logit} b_i \leftarrow \operatorname{logit} b_i + w(z)\, \operatorname{logit} q .\]

With a per-question temperature $T$ (\S{}5.4), $\operatorname{logit} q$ is replaced by $\operatorname{logit} q / T$. We use $\vert w\vert  = 1$. The sign and the zero cases are exactly the policy rules of \S{}3.3:

\begin{itemize}
\item $w = +1$ for \texttt{duplicate} and \texttt{refinement} (support)
\item $w = -1$ for \texttt{update}, \texttt{contradiction} and \texttt{negates} where \S{}3.3 permits a close
\item $w = 0$ for \texttt{new}, and for any answer a gate blocks
\end{itemize}
An open edge closes when $b_i <$ 0.25\src{src/engram/pipeline/belief.py} and reopens when $b_i >$ 0.60\src{src/engram/pipeline/belief.py}. The gap between the two gives hysteresis.

\textbf{Belief v3.} The v2 rule used in the held-out runs lets any answer count. A \texttt{duplicate} at $q < 0.5$ therefore has $\operatorname{logit} q < 0$ and \emph{lowers} belief, and a weak against-answer raises it. v3 counts an answer only when its label is the argmax and $q > 0.5$ (\S{}5.3). Figure~\ref{fig:3} traces one fact from the dev run under both rules.

\textbf{What this assumes.} The log-odds rule treats $q$ as a calibrated likelihood. Where the model is miscalibrated, belief moves by the wrong amount. This is why \S{}5.4 measures calibration and why a per-question temperature is part of the rule.

\subsection{Hygiene pass}
After ingestion, one pass re-checks every group of facts that share a subject and relation. It asks the yes/no question \texttt{same\_\allowbreak{}fact} for each pair, 50\src{src/engram/pipeline/hygiene.py} pairs per request. At $p \ge$ 0.85\src{src/engram/config.py} the pair is linked, and at $p \le$ 0.15\src{src/engram/pipeline/hygiene.py (1 − ACT\_THRESHOLD)} an existing link is dropped.

On the held-out conversations one pass made between 1,865\src{bench/results/e4\_belief\_v2\_\_heldout\_conv-30\_\_k3.json} and 5,446\src{bench/results/e4\_belief\_v2\_\_heldout\_conv-42\_\_k3.json} decisions, for between \$0.0112\src{bench/results/e4\_belief\_v2\_\_heldout\_conv-30\_\_k3.json} and \$0.0332\src{bench/results/e4\_belief\_v2\_\_heldout\_conv-42\_\_k3.json} (\S{}5.3). With LLM decisions, re-examining the store at that scale is what becomes unaffordable.

\subsection{Cost model}
With a per-decision Jev cost $c_J$, an LLM escalation cost $c_L$ and an escalation threshold $\theta$ on the top probability $q$:

\[C(\theta) = c_J + P(q < \theta)\, c_L ,\] \[E(\theta) = P(q \ge \theta)\, \varepsilon_J(\theta) + P(q < \theta)\, \varepsilon_L ,\]

where $\varepsilon_J(\theta)$ is Jev's error rate on the decisions it keeps and $\varepsilon_L$ is the LLM's error rate on the escalated ones. \S{}5.4 draws the empirical curve.

\section{Experimental setup}
\subsection{Models, data, caching and budget}
\textbf{Models} (the same in every arm):

\begin{itemize}
\item Extraction: \texttt{claude-haiku-4-5}.
\item Answers and judging: \texttt{claude-sonnet-4-6}, with mem0's LoCoMo evaluation prompts (Appendix B).
\item The LLM decision layer and all escalations: \texttt{claude-sonnet-4-6} with mem0's update prompt.
\item mem0 2.1.0 runs on \texttt{claude-haiku-4-5} with telemetry off.
\end{itemize}
\textbf{Slices:}

\begin{itemize}
\item \emph{dev}: conv-26 sessions 1--4, 76\src{bench/results/e2\_jev\_\_dev.json} messages, 35\src{bench/results/e2\_jev\_\_dev.json} questions.
\item \emph{stress}: conv-26 sessions 1--10, 215\src{bench/results/e2\_jev\_\_stress.json} messages, 80\src{bench/results/e2\_jev\_\_stress.json} questions.
\item \emph{held-out}: conv-30, conv-41, conv-42 and conv-43 whole, 610\src{bench/results/heldout\_report.json} questions. These were not used during development. The system configuration was frozen (git tag \texttt{e4-frozen}) before any held-out run.
\end{itemize}
LoCoMo's adversarial category is excluded throughout. Each held-out conversation is ingested once per system, and k=3 and k=20 are answered from the same store.

\textbf{Caching and budget.} Every LLM and Jev call is cached by its full request, and budget guards stop any run past a spending limit. Phase 2 (all experiments reported here) spent \$93.26\src{bench/results/phase2\_spend.jsonl} over 80\src{bench/results/phase2\_spend.jsonl} ledgered runs. Jev accounts for \$1.47\src{bench/results/phase2\_spend.jsonl} of it (\texttt{bench/results/phase2\_\allowbreak{}spend.jsonl}; per-arm totals in Appendix E). The build phase before it was not ledgered; the author's estimate for it is about \$10 [no file].

\subsection{The identical-extraction protocol}
For each message, mem0 2.1.0's \texttt{add()} builds its extraction prompt from:

\begin{itemize}
\item the new message, as \texttt{[date] speaker: text}
\item the last 10\src{src/engram/flags.py (extract\_last\_k, as mem0 2.1.0)} messages
\item the 10\src{src/engram/config.py} existing memories most similar to it
\item a current date
\end{itemize}
It passes no observation date, so relative dates in historical conversations resolve against the current date. We report this as-is, and a patched variant in \S{}6.

engram's E-arms build the same prompt with the same function (\texttt{generate\_\allowbreak{}additive\_\allowbreak{}extraction\_\allowbreak{}prompt}), inputs and model (\texttt{bench/run.py}, \texttt{src/engram/flags.py}). The ``existing memories'' differ only because each system's store differs. The E2 arms differ only in what decides after extraction.

\subsection{Update sets}
LoCoMo has almost no updates (\S{}2.3). Two update sets, written in the speakers' voices, extend it. Both are appended to the dev slice and were frozen by SHA-256 before any run.

\textbf{Set 1} (\texttt{bench/updates\_\allowbreak{}conv26.json}, SHA-256 prefix 2330876388f1\src{bench/updates\_conv26.json}) has 30\src{bench/updates\_conv26.json} items:

\begin{itemize}
\item 15\src{bench/updates\_conv26.json} easy closes
\item 10\src{bench/updates\_conv26.json} subtle items labeled \emph{no\_close}: past-tense mentions and unrealised plans
\item 5\src{bench/updates\_conv26.json} fulfilled plans
\end{itemize}
\textbf{Set 2} (\texttt{bench/updates2\_\allowbreak{}conv26.json}, prefix d4f3c8d2de61\src{bench/updates2\_conv26.json}) adds 28\src{bench/updates2\_conv26.json} messages and 20\src{bench/updates2\_conv26.json} questions:

\begin{itemize}
\item 5\src{bench/updates2\_conv26.json} point-in-time questions

\subsection{Statistics}
Both systems answer the same questions, so comparisons are paired: $d_i = \text{engram}_i - \text{mem0}_i$. We report:

\begin{itemize}
\item an exact McNemar test on the discordant questions
\item a 95\% interval from the per-question normal approximation
\item a cluster bootstrap that resamples the four held-out conversations. With four clusters, treat it as a robustness check.
\end{itemize}
The token-matched comparison reports the per-question interval only.

\section{Discussion}
\textbf{What the decision layer buys.}

\begin{itemize}
\item Cost and latency (\S{}5.1).
\item An audit trail: every decision has probabilities and a version.
\item Store operations that are reversible and gated (\S{}5.3).
\item A price at which re-examining the store is routine (\S{}3.5).
\end{itemize}
\textbf{What it does not buy.}

\begin{itemize}
\item Accuracy at default k: it ties (\S{}5.1).
\item Update-question accuracy on today's questions: every arm is near its ceiling (\S{}5.5).
\end{itemize}
\textbf{Benchmarks do not see storage correctness.} A question about a fact that changed is answerable from a store that kept both versions, as long as the memories carry dates. An evaluation that rewards a correct store would need:

\begin{itemize}
\item questions scored against validity windows
\item small retrieval budgets, where a stale fact displaces a current one
\item memories stored without dates
\item long chains of changes
\end{itemize}
Update set 2 targets these, and every arm is at its ceiling on it.

\textbf{Rerank or larger k.} Under a three-memory budget, a cheap listwise rerank is worth +8.7\src{bench/results/mem0\_token\_matched\_\_heldout\_pooled\_\_k6.json} points over mem0 at matched tokens. At k=20 the ranking stops mattering. For deployments that pay per context token, reranking is the cheaper route to the same accuracy.

\textbf{Threats to validity.}

\begin{itemize}
\item \emph{One baseline and one benchmark.} We compare only mem0 OSS 2.1.0, on four held-out LoCoMo conversations.
\item \emph{Author-written update sets.} The update sets and the regression pairs were written and labeled by the system's author.
\item \emph{One decision model.} Jev is the only decision model evaluated as the deciding backend, at one version. Laya was tested only as a zero-shot base checkpoint.
\item \emph{mem0's date handling.} mem0's open-source path gives no observation date, so relative dates resolve against the run date; the comparison uses it as shipped. A variant with the session date patched in scored 31/35\src{bench/results/mem0\_dated\_\_dev.json} on dev, against 30/35\src{bench/results/mem0\_\_dev.json} unpatched, within noise.
\item \emph{Dev-only rerank attribution.} The rerank attribution in \S{}5.2 rests on a dev ablation.
\item \emph{One judge model.} The judge is an LLM (claude-sonnet-4-6). We did not measure its agreement with human labels.
\end{itemize}
\section{Related work}
\textbf{Memory systems.} mem0 \citep{chhikara2025mem0} extracts and consolidates facts with LLM calls; its 2.x open-source default is add-only. Zep/Graphiti \citep{rasmussen2025zep} builds a temporal knowledge graph and invalidates edges with an LLM. MemGPT/Letta \citep{packer2023memgpt} manages memory tiers through LLM function calls. A-MEM \citep{xu2025amem} links notes with LLM-written attributes, and MAGMA \citep{jiang2026magma} organizes memory as multiple graphs. ByteRover \citep{nguyen2026byterover} resolves most queries through a five-tier progressive retrieval, in under 100\src{nguyen2026byterover (sub-100 ms tier resolution)} ms and without LLM calls, and escalates to agentic reasoning only for novel questions.

\textbf{Typed decisions in memory.} Jev-Mem \citep{jiang2026jevmem} is the closest design: Jev controls typing, relation construction, query routing, budget allocation, traversal, candidate scoring and stopping. The two designs differ in the store and in retrieval. Jev-Mem runs with admission filtering off and preserves every observation, so its store is never updated or closed; engram's store is governed by a close/belief policy with reversible closes and merges (\S{}3.3--3.4). Jev-Mem routes queries across multiple views; engram uses a single listwise rerank over cosine candidates plus a query-relation pull (\S{}3.1). The AtMem--Jev article \citep{taghia2026atmem} measured the rerank at the ranking level (Recall@10 unchanged; median batch latency 3.32\src{taghia2026atmem (median batch latency, s)} s) and reported no answer accuracy or intervals.

\textbf{Benchmarks.} LoCoMo \citep{maharana2024locomo} and LongMemEval \citep{wu2025longmemeval} evaluate long-term conversational memory. We used only LoCoMo.

\textbf{Reranking and context.} Long contexts are used poorly by language models \citep{liu2024lost}, and LLMs rerank candidates well \citep{sun2023rankgpt}; spending compute on selecting context rather than adding more of it follows from both, and our rerank result is an instance.

\textbf{Small models as decision layers.} Routers send queries to cheaper models \citep{ong2025routellm,chen2024frugalgpt}, and small classifiers act as guardrails \citep{inan2023llamaguard}. The escalation rule of \S{}3.6 is a router of that kind.

\textbf{Calibration and thresholds.} Temperature scaling \citep{guo2017calibration} and conformal prediction \citep{angelopoulos2021conformal} give principled thresholds for acting on a model's probability. \S{}3.4 depends on the former.

\section{Conclusion}
With extraction held identical, typed decisions replaced an LLM decision layer at 70.0$\times$\src{bench/results/e2\_llm\_\_dev.json ÷ bench/results/e2\_jev\_\_dev.json} lower cost and 27.6$\times$\src{bench/results/e2\_llm\_\_dev.json ÷ bench/results/e2\_jev\_\_dev.json} lower median decision latency, with no measured accuracy loss. On 610\src{bench/results/heldout\_report.json} held-out questions, a cheap listwise rerank gave +8.7\src{bench/results/mem0\_token\_matched\_\_heldout\_pooled\_\_k6.json} points over mem0 at matched context under a three-memory budget, and the systems tied at k=20. Closing stale facts, the part of the design aimed at correctness, did not change answers on current benchmarks. The base checkpoint of a small open-weights decision model, used zero-shot, did not make the relational decisions.

\paragraph{DEFAULT\_UPDATE\_MEMORY\_PROMPT (LLM decision layer and escalations)}
\begin{lstlisting}
You are a smart memory manager which controls the memory of a system.
You can perform four operations: (1) add into the memory, (2) update the memory, (3) delete from the memory, and (4) no change.

Based on the above four operations, the memory will change.

Compare newly retrieved facts with the existing memory. For each new fact, decide whether to:
- ADD: Add it to the memory as a new element
- UPDATE: Update an existing memory element
- DELETE: Delete an existing memory element
- NONE: Make no change (if the fact is already present or irrelevant)

There are specific guidelines to select which operation to perform:

1. **Add**: If the retrieved facts contain new information not present in the memory, then you have to add it by generating a new ID in the id field.
- **Example**:
    - Old Memory:
        [
            {
                "id" : "0",
                "text" : "User is a software engineer"
            }
        ]
    - Retrieved facts: ["Name is John"]
    - New Memory:
        {
            "memory" : [
                {
                    "id" : "0",
                    "text" : "User is a software engineer",
                    "event" : "NONE"
                },
                {
                    "id" : "1",
                    "text" : "Name is John",
                    "event" : "ADD"
                }
            ]

        }

2. **Update**: If the retrieved facts contain information that is already present in the memory but the information is totally different, then you have to update it. 
If the retrieved fact contains information that conveys the same thing as the elements present in the memory, then you have to keep the fact which has the most information. 
Example (a) -- if the memory contains "User likes to play cricket" and the retrieved fact is "Loves to play cricket with friends", then update the memory with the retrieved facts.
Example (b) -- if the memory contains "Likes cheese pizza" and the retrieved fact is "Loves cheese pizza", then you do not need to update it because they convey the same information.
If the direction is to update the memory, then you have to update it.
Please keep in mind while updating you have to keep the same ID.
